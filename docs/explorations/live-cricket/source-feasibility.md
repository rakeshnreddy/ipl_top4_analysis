# Live Cricket: source and model feasibility

Exploration only, 23 October 2026. Source reviewed at `357bcd1348eb9a161aa85aa52ae674bc59204f85`. This report proposes a separate Live Cricket section with **scores, model win probabilities and bookmaker prices**. It does not authorize a runtime service, provider purchase, account signup or deployment. No production files changed; no test suites, authenticated cricket/odds API calls or new installations were run.

## Decision summary

The current site supplies useful team identity, attribution, season tables and presentation primitives. It does **not** already contain a live-match feed or a match-win model. A scorecard product needs new ingestion/contracts; calibrated in-play probabilities need a separate model; bookmaker prices need a separate market provider and event mapping. Treat these as three independently available capabilities. A match can have a score without a full card, a card without deliveries, or a valid score without a supported model or market.

The existing static-only architecture can support an honestly labelled delayed snapshot pilot. Near-live refresh across many simultaneous matches needs a separately approved shared ingestion/cache service or another explicitly approved data-publishing mechanism. Increasing browser polling alone cannot update checked-in JSON or protect an API key.

## What provider documentation establishes, and what remains unproven

CricketData's public basic guide embeds example responses for `currentMatches` and `match_info`: match ID/type, teams, venue/start/status, and `score[]` with `r`, `w`, `o`, `inning`; match info also illustrates toss and winner. `fantasyEnabled` is documented as a **per-match** indication of scorecard/squad/ball-by-ball availability. This supports a capability flag, not a promise that every listed match has detail. [Basic API guide](https://cricketdata.org/how-to-use-cricket-data-api.aspx), [score explanation](https://cricketdata.org/cricket-live-score-api/).

The Fantasy guide's `match_scorecard` example adds innings batting rows (player ID/name, runs, balls, fours/sixes, strike rate, dismissal), bowling rows (player, overs, maidens, runs, wickets, wides/no-balls, economy), catching, extras and innings totals. The credited dismissal bowler is not proof of the currently active bowler. These are documentation samples, not an authenticated current contract or a measured live capture. The provider advertises ball-by-ball, but this review did not establish a current delivery endpoint's complete schema, correction semantics or availability across formats. [Fantasy API guide](https://cricketdata.org/how-to-use-fantasy-cricket-api.aspx), [provider FAQ](https://cricketdata.org/some-frequently-asked-questions-about-the-cricket-data-api-and-cricapi/).

The free plan advertises 100 daily hits and delayed data. One all-day request per minute alone is 1,440 requests, before pagination, match details or retries. A four-hour session with one list plus one card request per minute is 480 requests. Fantasy credit weighting and the actual account entitlement need checking before a pilot. Public latency descriptions differ, so no 30-second SLA is established here. [Pricing](https://cricketdata.org/pricing/), [current terms](https://cricketdata.org/terms-of-use/), [Fantasy trial policy linked by pricing](https://cricketdata.org/v1-0-launch-1st-may-2022/).

Cricsheet is a useful **historical training/replay** candidate. Its JSON describes players/registries, deliveries, extras, wickets, targets, powerplays and missing data. Its coverage page explicitly records gaps, with less extensive women's coverage. It is not an all-world live source. Preserve dataset attribution and notices; current JSON match data uses ODC-By, while XML has a different licence. [JSON specification](https://cricsheet.org/format/json/), [coverage](https://cricsheet.org/coverage/), [licensing](https://cricsheet.org/licensing/).

Bookmaker quotes are an additional source. The Odds API's example contract separates event, bookmaker, market and outcome price, and supplies update timestamps. Confirm the cricket competitions, live markets, settlement definitions and account access in the separate provider investigation. Its current terms allow customer-facing use but restrict standalone raw-data redistribution; the existing pattern of committing data into a public repository is not automatically an appropriate market-feed archive. A normal UI response and a downloadable bulk feed need distinct handling. [V4 contract](https://the-odds-api.com/liveapi/guides/v4/), [terms updated 31 August 2026](https://the-odds-api.com/terms-and-conditions.html).

## New contracts: keep four clocks and three products separate

Use a new versioned live contract rather than optional fields inside `IplSeasonPayload`:

| Object | Required proposal |
| --- | --- |
| `match` | Internal ID; provider IDs; competition/season; format; gender/category; international/club; teams; scheduled start; venue/time zone; status enum and raw provider status. Explicit pre-match, toss, live, innings break, rain delay, stumps, suspended, abandoned, completed and unknown states. Capabilities separately describe summary/card/deliveries/model/markets. |
| `scoreSnapshot` | Provider/revision, innings IDs and batting teams, runs/wickets, **integer legal balls**, allotted balls, target and target revision, striker/non-striker/active bowler only when supplied, result/method and completeness. Retain supplied overs notation; never treat `16.4` as 16.4 decimal overs. Do not synthesize unknown batter/bowler or target state. |
| `scorecard` / `deliveryEvent` | Stable player IDs and batting/bowling/extras/dismissals; innings/segment IDs, provider event ID or stable ordered sequence, revision/tombstone, legal-ball flag, batter/non-striker/bowler IDs, runs split and wicket kind/player/credit. Include super-over segments and correction/review events. A scorecard is not sufficient to reconstruct every event. |
| `modelPrediction` | Model/version, format/category support, training cutoff and calibration cohort, exact `inputSnapshotId`/target revision, outcome definition, probabilities, prediction time, uncertainty/support status. Explicit unsupported/stale states; no substituted 50/50 output when inference fails. |
| `marketQuote` | Provider, bookmaker ID/name, provider event ID and verified internal match mapping, market ID/key/period/line where applicable, outcome ID/meaning, **decimalPrice**, provider update time, `observedAt`, `inPlay: true/false/unknown`, market status and settlement metadata (draw/tie/super-over/no-result/void rules or explicitly unknown). Preserve source attribution and raw price format only where permitted. |

Maintain independent `providerUpdatedAt`, `observedAt` (successful ingestion), `publishedAt` and the model's `predictedAt`/input revision. If the source supplies no update time, keep it unknown; a newly fetched old score is not a new delivery. Score, card, delivery stream, model and each bookmaker market age independently. An old quote stays stale even beside a fresh score. Suspended, removed or missing markets must not become an active last price.

Match mapping must reconcile date/time changes, format, competition, gender and team identity across providers; name-only matching can join different fixtures. Ambiguous matches remain unmatched. Process duplicate/out-of-order events idempotently, accept explicit revisions and superseding snapshots, and recompute model results after score/target corrections. Keep raw receipt evidence only for approved retention. A win probability must identify the score revision it used; a changed `publishedAt` must not disguise stale inputs.

Bookmaker price and model probability are different quantities. `1 / decimalPrice` is a quoted implied probability that can include margin, rather than the site's estimate. Do not mix outcomes from different books/times into a synthetic complete market. Only compare a model and a quote when their outcome and settlement basis agree. No wager placement, operator accounts or betting links are needed for the requested informational view.

## Model scope and format gaps

- **T20/T20I:** build a separate state-conditioned baseline using innings, runs, wickets, legal balls remaining, chase target, pre-match team strength and available phase/venue information. First-innings inference needs a defend/chase model, rather than pretending a target already exists. Preserve tie/no-result and super-over rules. Train and evaluate before selecting additional player features.
- **ODI/one-day:** different 300-ball horizon, phases, resources and run environment require separate fitting/calibration. Relabelling the T20 model is not evidence of accuracy.
- **Tests/first-class:** need up to four main innings, draw/tie, lead/deficit, follow-on, declarations, day/session/time remaining and interruptions. The present two-innings/default-20 parser is structurally incompatible. Offer scorecards first if feasible; mark probabilities unsupported until this separate model is validated.
- **The Hundred/T10/other local formats:** explicit ball quota, scoring units and competition rules; five-ball sets or 100-ball innings cannot inherit ordinary T20 assumptions silently.
- **Women and associate/domestic cricket:** existing women’s league tables demonstrate configuration support, not calibrated player/match odds. Audit historical sample sizes and missingness by format/category/competition. Use measured pooling/shrinkage where justified, expose sparse-data support, and withhold unsupported probabilities rather than treating all teams as one men's-IPL population.
- **DLS, rain and live reviews:** consume official revised targets/quotas with provenance. The completed-NRR function is not a DLS engine. Pause or suppress predictions when target, restart allocation, review outcome or live state is unresolved; show the score/status independently. Do not invent an abandonment probability or recalculate an official target from an unverified formula.

Validation must split by **whole match and time**, keeping all snapshots of a held-out match out of training. Evaluate log loss, Brier score and calibration against simple baselines by format, innings/phase, category and sparse cohort; report sample sizes. Include replay cases for wides/no-balls, run-outs, injury retirements, replacements, super overs, revised targets, abandoned games and corrected deliveries. A large number of deliveries is not a large number of independent matches. Market prices can be a separately labelled comparison baseline, not an undisclosed model input or proof of correctness.

## Architecture options and constraints

| Option | Fit and trade-off |
| --- | --- |
| **A. Static-only delayed pilot** | Build normalized permitted snapshots ahead of deployment, keep API keys in Actions and show actual source age. Retains the existing no-runtime contract. Useful for match discovery, recent results, sample cards and replay/model validation. Current twice-daily cadence is not live; faster polling still has queue/build/deploy latency and requires an explicit budget. Quotes would need clear observed-time and expired/suspended handling, plus approved public-data retention. |
| **B. Optional shared data service** | Keep the site static; separately approve a scheduled/key-protected ingestion service that writes normalized cached snapshots and bounded UI responses. Centralize upstream polling, quotas, revisions and availability; serve both hosts from that cache. Never let each visitor or each CDN cache miss trigger unconstrained provider requests. This introduces runtime responsibilities and is an architecture decision, not something authorized by the existing static deployment. |

The present [workflow](../../../.github/workflows/update-ipl.yml#L1) runs at 07:00/19:30 UTC, shares deployment concurrency with code releases, commits changed data, runs Python/frontend tests, then builds and deploys both hosts. The scheduled gap reaches 12h30m before job/deployment delay. [GitHub documents](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows) that scheduled jobs can be delayed or dropped under load. The current [`/data/*` cache rule](../../../frontend/ipl-analyzer-frontend/public/_headers) also allows five minutes of caching. Do not reuse this entire release pipeline per ball.

Cloudflare documents 500 monthly Free Git-integrated Pages builds and one build at a time; this repository builds in GitHub and uses Wrangler Direct Upload, so verify actual account/deployment limits rather than assuming that number is its measured Direct Upload cap. Pages Functions use Workers quotas. Workers Free currently documents 100,000 daily requests and 10ms CPU; neither the site's account plan nor production inference cost was measured. Fit/train offline and budget any small inference separately. [Pages limits](https://developers.cloudflare.com/pages/platform/limits/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).

An edge cache is not automatically a global upstream quota guard: Cloudflare's Cache API is local to each data centre. Option B therefore needs a shared polling owner/budget and persistent last-good revision, not merely per-edge cache TTLs. Storage/scheduler choice is intentionally left to the architecture decision. Keep credentials out of Vite/browser bundles, logs and public payloads; validate provider IDs server-side and expose only licensed normalized UI data. The GitHub mirror needs an explicit shared-service URL/CORS policy; it cannot run Cloudflare Functions itself. [Cache API behaviour](https://developers.cloudflare.com/workers/runtime-apis/cache/).

## Bounded next stage

1. Choose delayed static scope or explicitly approve the shared-service exception, freshness goal, monthly spending ceiling and initial supported cohorts. Keep “all current world cricket” an eventual coverage goal, not a release claim.
2. Obtain owner-provided **entitlement/coverage evidence**, without sharing secret values: active-match pagination, detailed-card/delivery capabilities, API credit weighting, actual latency, bookmaker/market access, display and retention rights. Sample men/women, international/domestic/associate, T20/ODI/Test and a concurrent-match window. The discovery, score, delivery, model and market coverage intersections must each be measured.
3. Define adapters and the versioned contracts above with sanitized provider-approved fixtures and unsupported/missing states. Reconcile provider identities and settlement rules before showing model/market comparisons.
4. Build a local offline replay and first supported-format calibration study before any production win-probability claim. Keep a scorecard-only path for unsupported formats. Publish a per-capability coverage ledger and a go/no-go report with request budget and correction/freshness evidence.

The immediate blockers are verified detailed-feed/market entitlement, an agreed freshness/runtime budget, and a separately validated match model. None is resolved by the current secret's existence, historical ball availability, or the season solver's exactness.
